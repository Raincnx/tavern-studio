## 结论与置信边界

已找到直接的系统资源证据：10 月 18 日至少三次 ComfyUI 原生访问冲突附近，Windows Resource-Exhaustion-Detector 事件 2004 报告系统提交内存耗尽，且首要占用进程 PID 与当次崩溃的 Python PID 一致。应优先处理主机提交内存余量，而不是仅看显存利用率。

系统提交内存受 RAM 与分页文件额度共同限制，不等于 GPU 显存，也不等于当前物理 RAM 占用。

## 后续修复方向

1. 优先增加主机提交内存监测，在不足时拒绝开始新的加载，而不是等待进程崩溃后反复重启。
2. 评估分页文件额度与磁盘余量，留出至少覆盖实测峰值及其他程序波动的空间；本轮未修改 Windows 分页设置或关闭用户其他程序。
3. 继续定位编码器、量化主模型 CPU 缓存与 GPU 搬运的提交内存峰值；多次运行占用上涨尚不足以单独证明内存泄漏。
4. 若提交余量充分仍崩溃，再沿 torch_cpu/c10 的原生访问冲突获取转储并排查版本兼容，不把所有异常归为 OOM。

- 分辨率和 INT8 缓存实验沿用同一生产进程；cache-none 必须在队列空闲时重启，所以冷启动比较应参考原配置系统内存测量组。其他应用与系统分页状态未冻结，系统总提交量不能当成完全受控的模型独占数据。
- **部署 cache-none**：原生执行器不再长期保存已消费的节点结果，编码器等大对象能更早释放；每个新任务会重新执行加载节点。没有修改 ComfyUI 核心、模型权重、提示词、分辨率或步数。
- 两轮新结果分别与恢复原配置的两轮图片比较，解码后的 RGB 像素完全一致。此真实场景未损失画质，但重复任务耗时从约 53 秒增加到约 69–72 秒。
- 两轮最低系统提交余量为 9.76 / 12.68 GiB。第二轮进程峰值仍比首轮高，不能仅凭两轮宣称长期内存不增长或所有访问冲突已经修复。
- 本机启动脚本同步 `--cache-none`；其余保守开关不变。896 和 INT8 缓存没有部署，旧任务快照没有改写，Tavern 和私人数据未重启或改动。
